close the exposure the runtime ones open in the published 0.1.2 binary, and
release 0.1.3. Each step is one commit on `fix/dependency-advisories-0.1.3`,
merged with rebase.

### Exposure of the runtime advisories

- **GHSA-jm63-cq47-j5jp (shared server or transport): not affected.**
  `buildApp` passes `createServerFactory(deps)` to `createMcpHandler`, and
  the factory builds a new `McpServer` on every call, the case the advisory
  lists as safe. A new wire test sends two overlapping `tools/call` requests
  with the same JSON-RPC id and checks that each gets its own result. With a
  shared server patched in, the test fails.
- **GHSA-46jr-4wx8-v453 (validation memory): affected.** Our 1 MiB body cap
  is four times below the SDK default, but it does not bound validation
  work. Two input arrays had no length limit: `crm_metadata.sections` and
  `search_crm.kinds`. On `origin/main`, one 1 MiB `crm_metadata` call with
  `sections: ["x", ...]` (about 262 000 elements) grew RSS from 99 MB to
  1112 MB and returned a 46.8 MB validation error. Eight such calls fit the
  default concurrency of 8. On loopback without `MCP_AUTH_TOKEN` (the read
  default) any local process can send them; on a network bind, any holder
  of the token. The SDK fix needs our code: `maxToolInputElements` is off by
  default.
- **GHSA-mrhx-c7xc-m3w5 (Zod oversized collections): affected, same path.**
  Zod 4.6.6 checks `maxItems` before parsing elements, which helps only
  arrays that declare a maximum. The two unbounded arrays above needed one.
- **GHSA-rvq5-wwqv-78pq (bearer audience): not affected.** We do not call
  `requireBearerAuth` or `verifyBearerToken`. `src/server/auth.ts` compares
  one operator-configured static token in constant time; no authorization
  server issues it, so there is no audience to confuse.
- **GHSA-5r4p-p66f-jhc7 (Hono serveStatic): not affected.** No code uses
  `serveStatic`; the app serves `/health` and `/mcp` only.

### SDK 2.0.0 to 2.3.1 behavior changes

Read from the release notes of 2.1.0, 2.2.0, 2.3.0 and 2.3.1:

- 2.1.0 refuses a modern (2026-07-28) POST without `MCP-Protocol-Version`
  with 400 / -32020. 2.0.0 served it. New wire test.
- 2.1.0 caps SDK-read bodies at 4 MiB and batches at 100 messages. We pass
  `parsedBody` for JSON, so the SDK reads nothing, and we reject every batch
  before dispatch. A probe of batch bodies sent as `text/plain`, without a
  content type, as `application/json-seq`, as `application/vnd.api+json`
  and with a UTF-8 BOM found no path to dispatch: the BOM case hits our
  batch rejection, the rest get the SDK's 415.
- 2.3.0 serves one connection per `Server`; see GHSA-jm63 above.
- 2.3.0 relicenses the SDK to Apache-2.0. The bundled binary now carries
  Apache-2.0 code next to MIT code; the npm install still pulls the SDK
  package with its `LICENSE` as a declared dependency.
- Nothing else touches this server: no prompts, no `x-mcp-header`, no
  scope challenges, no SDK bearer auth.

## Tasks

1. **Runtime pins.** Change the pin expectation in
   `tests/package-contract.test.ts` first, then bump `package.json` and
   refresh `bun.lock`. Bun keeps the old zod and hono as nested copies for
   the conformance tree; delete those three nested records so everything
   dedupes onto the patched versions. Add the wire tests for the missing
   protocol header and the overlapping same-id calls.
2. **Bounded tool input.** Tests first in `tests/server/modern-wire.test.ts`:
   every listed tool's input schema has a finite largest valid size (array
   elements plus object members) under `MAX_TOOL_INPUT_ELEMENTS`, and a call
   over the cap is refused with no tool work. Then export
   `MAX_TOOL_INPUT_ELEMENTS = 2000` from `src/server/mcp.ts`, pass it as
   `maxToolInputElements`, and add `.max()` to `sections` and `kinds` at
   their enum sizes (both are deduped, so no valid call loses anything). The
   largest valid input is a full `create_records` batch at 1326 elements.
   `docs/security.md` gets the MUST in par. 2 and requirement 17 in par. 10.
3. **Development tree.** Remove the `body-parser`, `body-parser/content-type`,
   `ip-address`, `undici` and `fast-uri` records from `bun.lock` and
   reinstall with the release-age floor. Only the conformance tree changes.
4. **Release 0.1.3** per `docs/releasing.md` on PR #7: package, both
   `server.json` versions, README links and `bunx` pin, `SECURITY.md`, and
   the pins in `tests/release-metadata.test.ts` and
   `tests/package-contract.test.ts`.

Gate before the release commit: cold `bun install --frozen-lockfile`,
`bun audit` with no findings, typecheck, `bun test`,
`bun run test:security`, `git diff --check`, the conformance baseline and a
read-only sandbox smoke.
