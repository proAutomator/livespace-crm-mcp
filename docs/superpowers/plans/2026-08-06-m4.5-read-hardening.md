# M4.5 Read Hardening - Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Execute ONLY your assigned task; do not touch files outside its list. If a step conflicts with reality, record the deviation in your report instead of improvising.

**Goal:** Fix two defects found by real MCP-client testing after M4: (1) retried reads reuse a spent Livespace session and fail with a MISLEADING `AUTH_FAILED (561)` - every retry must sign a fresh attempt; (2) `detail: "minimal"` returns the full record shape with blanked values instead of omitting fields, wasting context and telling the model "not filled in" about fields that were never requested.

**Architecture:** Restructure `src/livespace/client.ts` so the retry loop wraps the WHOLE composite attempt (token fetch -> signature -> signed POST) via a `prepare()` callback, with a single-attempt HTTP primitive underneath. `projectRecord` in `src/livespace/records.ts` switches from blank-fill to key OMISSION; the zod record schemas relax non-core fields to `.optional()`. No new dependencies, no new env vars.

## Live evidence (2026-08-06, isolated on the sandbox)

1. **The 561 bug (reproduced 3 ways on the same 162-deal window fetch, ~2 MB):**
   default client (timeout 15 s, retries on): first call OK in 13.8 s, second
   call `AUTH_FAILED (561)`; timeout 60 s: three of three OK (17-19 s);
   retries off: honest `TIMEOUT` every time. Mechanism: `call()` mints
   `_api_sha`/`_api_session` ONCE and `post()` retries the same signed body;
   when attempt 1 times out client-side the server still consumed the
   session, so the replay is rejected as 561 and the model is told to check
   its API credentials. NOTE: this poisons EVERY signed-call retry (5xx too),
   not only timeouts - the M2.5 retry tests passed only because fake fetches
   do not validate sessions.
2. **Latency/size reality:** Livespace serializes a deal at ~13 KB.
   `Deal/getAll` limit 5 -> ~1.2 s; limit 50 -> ~6 s; limit 200 (162 rows,
   1.97 MB) -> 14-19 s. The default 15 s timeout sits BELOW an honest
   SORT_WINDOW fetch.
3. **Minimal detail waste:** 5 deals at `detail: "minimal"` = 2555 bytes,
   28 keys per item, only 7 non-empty; `standard` = 4168 bytes. The blanked
   fields also collide with the server's own instruction that empty values
   mean "not filled in".

## Global Constraints

- All M0b-M4 constraints apply (English, TDD, synthetic fixtures, offline unit tests, `{code, message, hint}` errors, counts-only text channel, no new deps/env vars, never push).
- Retry classification stays EXACTLY as today: only transport-shaped failures retry (`TIMEOUT`, `NETWORK_ERROR`, `RATE_LIMITED`, `UPSTREAM_ERROR` from HTTP 5xx); business envelope errors (AUTH_FAILED, VALIDATION_ERROR, PERMISSION_DENIED, BAD_PARAMS...) fail fast on the first composite attempt. A REAL credential problem must not be retried into extra load.
- Write semantics preserved bit-for-bit: `{write: true}` -> ONE composite attempt; a transport failure of the SIGNED POST (after dispatch) -> `WRITE_OUTCOME_UNKNOWN`; a failure BEFORE the signed POST is dispatched (token fetch, signing) -> the plain classified error, because nothing was sent (docs/security.md par. 5).
- Cancellation semantics preserved: signal-state checks, `cancelledError()`, abort never retried, the M2.5/M3 seams untouched.
- Jitter/backoff/Retry-After behavior preserved (capped full jitter, `Retry-After` honored, `random` injectable).
- Empty-value semantics: WITHIN a requested detail level, empty strings/nulls still mean "not filled in" and are returned; fields OUTSIDE the requested level are now ABSENT. The line between the two is the projection whitelist (unchanged key sets from M4).

### Task 1: Per-attempt signing and honest read timeouts

**Files:**

**Interfaces:**
- Produces (signature changes only where listed; everything else identical):

```ts
// errors.ts - one optional readonly field appended to the constructor:
export class LivespaceError extends Error {
  constructor(code, message, hint, resultCode?, readonly retryAfterMs?: number) {...}
}

// client.ts
export interface LivespaceClientOptions {
  fetchImpl?; timeoutMs?: number;  // DEFAULT CHANGES: 15_000 -> 30_000
  maxAttempts?; sleep?; random?;
}
export interface LivespaceCallOptions {
  signal?: AbortSignal; write?: boolean;
  timeoutMs?: number;   // NEW: per-call override of the per-attempt timeout
}
```

Internal restructure (exact design):

1. `singleFetch(url, body, opts: { timeoutMs, signal }): Promise<Envelope>` -
   ONE HTTP attempt: combineSignals(AbortSignal.timeout(timeoutMs), signal),
   fetch, then classify: aborted-caller -> `cancelledError()`; HTTP 429 ->
   `RATE_LIMITED` with `retryAfterMs` parsed from the header; HTTP >= 500 ->
   `UPSTREAM_ERROR` with `retryAfterMs`; TimeoutError -> `TIMEOUT`; other
   throw -> `NETWORK_ERROR`; else parse and return the envelope. (This is
   today's per-attempt body of `post`, extracted, with Retry-After now
   carried ON the error.)
2. `getToken(opts): Promise<{token, sessionId}>` - ONE `singleFetch` of the
   token endpoint + today's envelope/shape validation (business failures
   throw via `errorFromEnvelope` / AUTH_FAILED as today). No internal retry
   loop anymore - the composite loop below owns retries.
3. `post(prepare: () => Promise<{url, body, signedDispatch: boolean}>, opts: {write, signal, timeoutMs?})`
   - the retry engine. Each attempt: signal-state check; `await prepare()`
   (fresh token + fresh signature for signed calls); `singleFetch`. Track
   whether the failed phase had `signedDispatch` (the signed POST) for the
   write-outcome rule. Retryable codes (list above) retry for reads with
   `retryDelayMs(attempt, error.retryAfterMs)`; non-retryable rethrow
   immediately; writes never loop. After exhaustion: write + signed-POST
   transport failure -> `WRITE_OUTCOME_UNKNOWN` (as today); otherwise the
   last classified error.
4. `call()` - unchanged surface; `prepare` closes over module/method/params
   and does `getToken` -> `buildSignature` -> body, so EVERY attempt gets a
   fresh `_api_session`/`_api_sha`. Envelope business validation stays in
   `call` after `post` returns (never retried). The whole composite still
   runs inside ONE throttle slot with the caller signal (unchanged).
5. `records.ts` large-page rule (the ONLY records change in this task): in
   the list fetchers, pass `timeoutMs: LARGE_PAGE_TIMEOUT_MS` (60_000, a
   named constant with a comment citing the measured 14-19 s for a 200-row
   window) to `client.call` when `limit >= 100`; otherwise leave the client
   default. `listTasks` (fixed 50-row pages, ~6 s observed) keeps defaults.
