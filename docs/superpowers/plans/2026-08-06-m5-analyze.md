# M5 `analyze` - Implementation Plan (rev. 2 after critique panel)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Execute ONLY your assigned task; do not touch files outside its list. If a step conflicts with reality, record the deviation in your report instead of improvising.

**Goal:** One read tool `analyze` with four named server-side aggregations - `pipeline_summary`, `stage_conversion`, `activity_summary`, `forecast_vs_realization` - computed over bounded fetch windows, because the Livespace API has no aggregations of its own.

**Architecture:** `src/livespace/aggregate.ts` owns bounded window fetchers (multi-page sweeps over the M4 fetchers with dedupe, a wall-clock deadline and explicit truncation) and pure aggregation functions (mapped records in, envelope rows out; every period filter applied LOCALLY). The tool lives in `src/server/tools/analyze.ts`: flat input schema, per-analysis strict output envelopes, runner that joins windows + aggregators + the metadata processes section (for pipeline stage order). No caching of record data or computed aggregates (docs/security.md par. 8); the only cached input is the dictionary `processes` section, read through the existing `MetadataService`, and its `{asOf, stale}` freshness travels into the answer. Registration order becomes: health, crm_metadata, search_crm, get_records, get_activity, analyze.

**Tech Stack:** unchanged, no new dependencies. Zod idiom as in M3/M4: `z.strictObject` everywhere, per-analysis optional envelopes on ONE output schema root, NEVER a union of look-alike shapes (zod picks the first match and strips fields), NEVER `z.discriminatedUnion` as an inputSchema root (emits `oneOf` without `"type": "object"` - not a valid MCP inputSchema).

## Live-verified API evidence (probe runs 2026-08-06 on the sandbox)

All numbers measured live; values below are synthetic where they are values.

1. Deal volumes and latency: open=162 (8.8 s at limit 200), won=9 (0.8 s),
   lost=131 (12.9 s), `status: "all"`=200 = the window cap, NOT the total
   (302). Pages of 100: 8.1 s + 3.3 s, offset paging exact, no overlap.
2. `status_change_date` is filled ONLY on won/lost deals (162/162 open have
   ""). It can be LATER than `modified` (sandbox sample: status_change
   2025-10-12 vs modified 2025-10-09), so a `modified` pre-filter on
   closed-deal windows would drop rows - date filtering on deals is LOCAL
   ONLY.
3. NO server-side date filter works on `Deal/getAll` except `modified`:
   `status_change_date_from`, `status_change_from`, `date_from`,
   `created_from`, `date_end_from` are all accepted and IGNORED (probed with
   a future date; counts unchanged).
4. NO stage history exists: `Deal/getHistory`, `Deal/getStageHistory`,
   `Deal/getChanges`, `History/getList` all fail 540. Stage changes exist
   only as Polish free-text wall entries ("zmienił(a) etap szansy ...") -
   not machine-usable. Any conversion metric is therefore a POINT-IN-TIME
   estimate from current stage positions.
5. Deal `stage_id` is a MAIN-STAGE id and `substage_id` is a checkbox-step
   id: against `Deal/process_getList`, 147/147 non-empty stage_ids resolved
   to main stages (0 nested, 0 miss, 0 name mismatches) across
   open/won/lost.
6. Won deals RETAIN their stage (sandbox: all 9 at the final stage). Lost
   deals SOMETIMES lose it (25/131 empty). Open deals can lack a stage too
   (30/162, all in one process); filtering by that process's first stage id
   returns 0 rows, so the empty-stage rows are NOT first-stage rows
   renamed - they are genuinely unassigned. Aggregations bucket them as
   `unassigned`, never guess.
7. `processes` x `status` filter combos work (scalar process id): sandbox
   Inbound open=98 won=1 lost=77, Outbound 15/1/9, Realizacja 0/0/0,
   Sprzedaż 49/7/45.
8. `probability` is never empty on the sandbox and "0,00" is a REAL zero
   (`parseCommaDecimal` returns 0, not null). `value` never empty either;
   `date_end` empty on 3/162 open deals; single currency (PLN) on the
   sandbox but multi-currency orgs exist.
9. `Wall/getList` feed: date range is honored and INCLUSIVE ON BOTH ENDS
   (a single-day range returned exactly that day's rows; a future range
   returned 0). 410 total rows since 2019, sorted desc by `date`, honors
   `limit` above 200 (limit=500 returned 410) and `offset` (second page
   exact). Light rows: ~1.1 s per 200. `type_name` values seen: `activity`,
   `email`, `phone`, `note`; `creator_name` always present.
10. `Todo/getTodoObjects`: fixed 50-row pages (M4 fact), `isCompleted`
    filter works both ways, `type_name` is often empty (30/50 on one
    sandbox page). `datesPeriod {from, to}` FILTERS on the task's
    `date_from`, but `to` is EXCLUSIVE at day granularity: from=X to=X and
    from=X-1 to=X both return 0 for a day known to hold tasks, while
    from=X to=X+1 returns exactly day X's tasks. A month-wide range
    matches rows across the month. Upstream ranges must therefore be sent
    WIDENED (`to` + 1 day) and re-filtered locally to the documented
    inclusive period.
11. `Deal/process_getList` returns a keyed object
    `{<processId>: {name, main_stages: {<stageId>: {name, stages:
    {<stepId>: {name}}}}}}` - ids are KEYS, emission order = pipeline order
    (M3 fact). The cached `processes` section already maps this to
    `ProcessInfo {id, name, stages: [{id, name, steps}]}`.
12. `probability` is a 0-100 percentage: open window min 0, max 80; won
    samples include "100,00". Guard anyway: a row whose probability parses
    outside [0, 100] must not be multiplied into a forecast.
13. `Deal/getAll` default emission order is `created` DESC (verified across
    a page boundary; `modified` and name are NOT sorted). A truncated deal
    window therefore drops the OLDEST deals - but old open deals can still
    close or end inside any period, so truncation still invalidates
    period-derived numbers (decision below).

## Global Constraints

- Explicit `limit` on every list/search call upstream; local caps are
  authoritative (AGENTS.md; docs/security.md par. 3). The ONE documented
  exception: `Todo/getTodoObjects` has no limit parameter (fixed 50-row
  pages) - `TASK_WINDOW_MAX_PAGES` is the load control there, and the
  regression tests pin the limits the other calls send
  (docs/security.md par. 10 item 8).
- Counts-only markdown text channel: NO CRM-authored string (process names,
  stage names, user names, type names) ever enters `result.text`
  (docs/security.md par. 4). They live in `structuredContent` as typed data.
- Errors surfaced to the model are `{code, message, hint}` with our fixed
  wording only - never upstream bodies (par. 6). Non-LivespaceError throws
  collapse via the shared `toToolError`.
- CANCELLED contract (repo idiom, M3/M4): a cancelled call NEVER returns a
  tool result. At every catch site: `if (opts.signal?.aborted) throw
  cancelledError();` and if a mapped entry's code is CANCELLED, throw
  `cancelledError()` too.
- NO caching of record data or aggregates computed from it (par. 8):
  `src/livespace/aggregate.ts` and `src/server/tools/analyze.ts` MUST NOT
  import any cache module (regression: source must not match
  `/from\s+"[^"]*cache\.js"/` - the path differs per directory, so the
  regex, not a fixed string). The `processes` dictionary section IS
  cacheable and is read through the existing `MetadataService` only.
- Wall-clock budget: `ANALYZE_BUDGET_MS = 60_000` per analyze call. Window
  sweeps stop paging (truncated, not an error) once the deadline passes;
  the arithmetic that forces this: one 100-row deal page measured 3-9 s,
  a worst-case analysis is 3 windows x 5 pages through a 2-slot throttle
  with a 60 s dispatch timeout and up to 3 attempts each - unbounded, this
  can run many minutes.
- `null` value/probability means "not filled in" - NEVER treated as zero in
  a sum or average; every aggregate reports how many rows it skipped.
- Every tool config carries
  `annotations: { readOnlyHint: true, destructiveHint: false, idempotentHint: true, openWorldHint: false }`
  (house convention; an existing wire test asserts annotations on every
  listed tool).
- Every fake credential in tests MUST contain the word "synthetic"
  (gitleaks allowlist).
- zod: `import * as z from "zod/v4"`; strictObject everywhere; no unions of
  look-alike shapes; no discriminatedUnion inputSchema root.
- TDD per task, one commit per task, `bun test` + `bun run typecheck` green
  before every commit. Baseline: 508 tests.

## Design decisions locked by probe evidence and the critique panel

- **Windows, not totals.** Livespace reports no totals anywhere. Every
  aggregation fetches a bounded window and reports
  `basedOn: {fetched, truncated}` per source. Budgets: deals - pages of 100
  (the M4.5 60 s large-page timeout applies at that limit), max 5 pages =
  500 rows PER STATUS window; feed - pages of 200, max 5 pages = 1000
  entries; tasks - fixed 50-row pages, max 10 pages = 500 tasks. Pages
  within one window are sequential (offset chain); the up-to-three status
  windows of one analysis run concurrently via `Promise.all` - the client
  throttle (2 concurrent, 150 ms spacing) is the upstream guard.
- **One deadline, one abort.** The runner computes
  `deadlineAt = Date.now() + ANALYZE_BUDGET_MS` and creates ONE
  `AbortController` whose signal is combined with the caller's
  (`AbortSignal.any`). Every window fetch receives that combined signal AND
  `deadlineAt`; a window checks the deadline BEFORE every page after the
  first (the first page always runs) and stops with `truncated: true`.
  When any window of a `Promise.all` group rejects, the runner aborts the
  controller so sibling sweeps stop instead of paging on after the call
  has already failed.
- **A truncated window invalidates derived numbers.** The window is a
  created-DESC prefix (evidence 13), so a local date filter over a
  truncated window can miss any part of the period, and a cross-stage
  ratio over a truncated fetch compares incomplete populations. Rule: when
  any contributing deal window is truncated, `summarizeForecast` nulls
  `forecast.value.sum`, `weightedValueSum`, `realization.won.value.sum`
  and `realization.lost.value.sum`, and `summarizeStageConversion` nulls
  every `conversionFromPrevious`. Counts stay (they are honest partials)
  and `basedOn.truncated` flags them. Pipeline stage sums stay numeric -
  they are additive partials of an un-filtered scope, flagged the same
  way.
- **Dedupe by id when accumulating deal and task windows.** Offset paging
  over live data can re-deliver a row when rows shift between pages; a
  double-counted deal corrupts a sum silently. `fetched` reports unique
  rows.
- **Per-status fetches, never `status: "all"`.** Evidence 1: "all" hits the
  window cap first and hides the split we need anyway.
- **Every period is applied LOCALLY, upstream date params are load hints.**
  Deals: no upstream date filter exists (evidence 2-3) - `date_end` /
  `status_change_date` filtering is local via `inPeriod`. Feed: upstream
  range honored and inclusive (evidence 9) - sent as-is AND re-filtered
  locally (belt and braces). Tasks: upstream `datesPeriod` is to-EXCLUSIVE
  (evidence 10) - sent WIDENED (`to` = dateTo + 1 day via `dayAfter`) and
  re-filtered locally on `date_from` to the inclusive period. The
  summaries report what the local filter dropped.
- **Currency honesty, scoped to contributing rows.** A sum over mixed
  currencies is a lie, but only rows that CONTRIBUTE to a sum (non-null
  `value`) can mix it: the sum is `null` when its contributing rows carry
  more than one distinct `currency` string ("" is a distinct value); rows
  with a null value only increment `missing` and never influence the sum
  or the mixing check. `totals` runs the check over ALL its contributing
  rows, NOT by adding stage sums - stage A all PLN + stage B all EUR means
  numeric stage sums and a null total. Each envelope lists `currencies`
  (distinct values over ALL fetched deals of the analysis, sorted). Counts
  are never nulled.
- **stage_conversion is an estimate and says so** (evidence 4): computed
  from current positions with fixed `assumptions` strings in the output.
- **All-or-nothing per analysis, except activity_summary.** A pipeline or
  forecast answer with a missing status window is a silently wrong number,
  so any failed deal window fails the call (`isError: true`).
  `activity_summary` has two independent sources (feed, tasks); one may
  fail and the other still answers, with an `errors[]` entry - the M3
  partial-results idiom. If EVERY source failed and every failure is
  CANCELLED, throw `cancelledError()` instead (Global Constraints).
- **Deterministic output ordering**: processes in metadata emission order
  (= pipeline order source), stage rows in pipeline order, `byType`/
  `byUser` rows by count desc then name asc (PLAIN `<`/`>` code-unit
  compare, NOT localeCompare - locale-dependent output is nondeterminism),
  `currencies` sorted, unknown-process buckets one per distinct
  `processId` ordered by first appearance in the deal array.
- **Dictionary staleness is visible.** `pipelineSummary` and
  `stageConversion` carry `processes: {asOf, stale}` from the
  `SectionResult`, and a fixed assumption explains that a stage created
  after the last refresh lands under `unassigned`.

### Task 1: Bounded window fetchers

**Files:**
- Create: `src/livespace/aggregate.ts`
- Test: `tests/livespace/aggregate-windows.test.ts`

**Interfaces:**
- Consumes: `RecordFetchers` (`listDeals`, `listTasks`), `ActivityFetchers`
  (`crmFeed`), `DealRecord`, `TaskRecord`, `WallEntry`, `LivespaceError`.
- Produces (exact exports Tasks 2-3 rely on):
  - `DEAL_WINDOW_PAGE = 100`, `DEAL_WINDOW_MAX_PAGES = 5`,
    `FEED_WINDOW_PAGE = 200`, `FEED_WINDOW_MAX_PAGES = 5`,
    `TASK_WINDOW_MAX_PAGES = 10`
  - `interface Window<T> { rows: T[]; fetched: number; truncated: boolean }`
  - `dayAfter(date: string): string` - "2026-08-06" -> "2026-08-07",
    correct across month/year ends (UTC arithmetic:
    `new Date(date + "T00:00:00Z")` + 86_400_000 ms, slice ISO to 10).
  - `fetchDealWindow(records: RecordFetchers, opts: { status: "open" | "won" | "lost"; processId?: string; deadlineAt?: number; signal?: AbortSignal }): Promise<Window<DealRecord>>`
  - `fetchFeedWindow(activity: ActivityFetchers, opts: { dateFrom: string; dateTo: string; deadlineAt?: number; signal?: AbortSignal }): Promise<Window<WallEntry>>`
  - `fetchTaskWindow(records: RecordFetchers, opts: { dateFrom: string; dateTo: string; deadlineAt?: number; signal?: AbortSignal }): Promise<Window<TaskRecord>>`

**Behavior:**
- `fetchDealWindow`: loop up to `DEAL_WINDOW_MAX_PAGES` pages of
  `listDeals({status, processId?, limit: DEAL_WINDOW_PAGE, offset, signal})`
  (NO `processId` key at all when unscoped - the fakes assert the exact
  options object). Accumulate `items` deduped by `id` (a `Set`; later
  duplicates dropped). Advance
  `offset += Math.min(page.rawCount, DEAL_WINDOW_PAGE)` - the M4 cursor
  rule, so an endpoint that ignored the limit cannot loop forever. Stop
  when `page.hasMore === false`, or when `page.rawCount === 0` (guards a
  hasMore-true empty page from looping), or - before every page AFTER the
  first - when `opts.deadlineAt !== undefined && Date.now() >= deadlineAt`
  (stop with `truncated: true`). `truncated = true` iff the loop stopped
  with `hasMore` still true (page cap or deadline).
  `fetched = rows.length` (unique). `truncated` is deliberately
  conservative: a window holding exactly `PAGE * MAX_PAGES` rows reports
  `truncated: true`, because upstream reports no totals - one wasted page
  of headroom would cost more than the flag.
- `fetchFeedWindow`: same loop shape over
  `crmFeed({dateFrom, dateTo, limit: FEED_WINDOW_PAGE, offset, signal})` -
  dates passed through VERBATIM (upstream range is inclusive, evidence 9),
  max `FEED_WINDOW_MAX_PAGES` pages, no dedupe (feed ids are not record
  ids; the offset chain is the guarantee), advance by
  `Math.min(rawCount, FEED_WINDOW_PAGE)`, same deadline rule.
- `fetchTaskWindow`: loop `page = 1..TASK_WINDOW_MAX_PAGES` over
  `listTasks({page, dateFrom, dateTo: dayAfter(opts.dateTo), signal})` -
  the upstream `to` is EXCLUSIVE (evidence 10), so it is widened here; the
  Task 2 summarizer re-filters locally to the inclusive period. NO
  `completed` key (the summary splits locally). Stop when
  `hasMore === false` or `rawCount === 0` or the deadline rule. Dedupe by
  `id`.
- All three: no try/catch - errors from the fetchers propagate to the
  caller untouched (the tool layer maps them). No imports from any cache
  module. Module header comment states the contract: bounded sweeps,
  dedupe, deadline, explicit truncation, no caching (par. 8), and the
  tasks-have-no-limit exception (par. 3).

### Task 2: Pure aggregators

**Files:**
- Modify: `src/livespace/aggregate.ts` (append; Task 1 exports unchanged)
- Test: `tests/livespace/aggregate-summaries.test.ts`

**Interfaces:**
- Consumes: Task 1 types; `DealRecord`, `TaskRecord`, `WallEntry`,
  `ProcessInfo` (from `./metadata.js`).
- Produces (exact exports Task 3 relies on):
  - `interface Period { from: string; to: string }`
  - `interface ValueStats { sum: number | null; missing: number }`
  - `interface StageSummaryRow { stageId: string; stageName: string; position: number; dealCount: number; value: ValueStats; avgProbability: number | null; probabilityMissing: number }`
  - `interface ProcessSummary { processId: string; processName: string; stages: StageSummaryRow[]; unassigned: { dealCount: number; value: ValueStats }; totals: { dealCount: number; value: ValueStats } }`
  - `interface PipelineSummary { processes: ProcessSummary[]; currencies: string[]; totalOpenDeals: number }`
  - `summarizePipeline(deals: DealRecord[], processes: ProcessInfo[]): PipelineSummary`
  - `interface ConversionRow { stageId: string; stageName: string; position: number; openCount: number; lostCount: number; wonCount: number; reachedCount: number; conversionFromPrevious: number | null }`
  - `interface StageConversion { processId: string; processName: string; stages: ConversionRow[]; outcomes: { openCount: number; wonCount: number; lostCount: number }; unassigned: { openCount: number; wonCount: number; lostCount: number } }`
  - `summarizeStageConversion(open: DealRecord[], won: DealRecord[], lost: DealRecord[], process: ProcessInfo, truncated: boolean): StageConversion`
  - `interface CountRow { name: string; count: number }`
  - `interface FeedSummary { total: number; byType: CountRow[]; byUser: CountRow[]; outOfPeriodCount: number }`
  - `summarizeFeed(entries: WallEntry[], period: Period): FeedSummary`
  - `interface TaskSummary { total: number; completedCount: number; openCount: number; byType: CountRow[]; outOfPeriodCount: number; noDateCount: number }`
  - `summarizeTasks(tasks: TaskRecord[], period: Period): TaskSummary`
  - `interface ForecastSide { dealCount: number; value: ValueStats; weightedValueSum: number | null; weightedMissing: number; noDateEndCount: number }`
  - `interface RealizationSide { won: { dealCount: number; value: ValueStats }; lost: { dealCount: number; value: ValueStats }; noStatusChangeDateCount: number }`
  - `interface ForecastVsRealization { forecast: ForecastSide; realization: RealizationSide; currencies: string[] }`
  - `summarizeForecast(open: DealRecord[], won: DealRecord[], lost: DealRecord[], period: Period, truncated: boolean): ForecastVsRealization`
  - `inPeriod(dateText: string, period: Period): boolean`

**Behavior (all functions pure, no I/O, no clock reads, inputs never
mutated):**
- Shared value math (one internal helper): a sum covers rows with non-null
  `value`, rounded to 2 decimals; `missing` counts null-value rows. The
  sum is `null` (missing still counted) when the CONTRIBUTING rows
  (non-null value only) carry more than one distinct `currency` string
  ("" is a distinct value). Null-value rows never influence the sum OR the
  mixing check. Zero contributing rows -> sum 0. `totals` and every other
  multi-scope sum runs the check over its own contributing rows - NEVER by
  adding sub-sums. `currencies` on an envelope = sorted distinct
  `currency` of ALL deals the analysis fetched (value-less rows included
  here).
- `inPeriod`: takes the first 10 chars of `dateText` (handles both
  "YYYY-MM-DD" and "YYYY-MM-DD HH:mm:ss+TZ"), returns
  `from <= d && d <= to` by string compare (ISO-lexicographic). Empty text
  is never in period.
- `summarizePipeline` (open deals only): one `ProcessSummary` per
  `ProcessInfo` in metadata order, EVERY stage listed in pipeline order
  even at 0 count. A deal joins its process by `processId`, its stage row
  by `stageId`. Deals whose `processId` matches no `ProcessInfo` form
  trailing `ProcessSummary` buckets - ONE per distinct unknown
  `processId`, ordered by first appearance in the deal array,
  `processName` from the first such deal row, `stages: []`, all its deals
  in `unassigned`. Empty `stageId`, or a `stageId` not in that process's
  stages, goes to `unassigned`. `avgProbability`: mean of non-null
  probabilities rounded to 2 decimals, `null` when no rows have one.
  `totals` covers all deals of the process (stage rows + unassigned).
  Processes with 0 deals keep their (all-zero) rows - the shape of the
  pipeline is the answer. `totalOpenDeals = deals.length`.
- `summarizeStageConversion`: positions from `process.stages` order. For
  each stage i: `openCount`/`lostCount`/`wonCount` = deals AT that stage
  (by `stageId`); `reachedCount` = deals (any of the three statuses) whose
  stage position >= i; `conversionFromPrevious` =
  `round4(reached_i / reached_{i-1})` for i > 0, `null` for i = 0 or when
  `reached_{i-1} === 0`, and null for EVERY row when `truncated` is true
  (design decision: a truncated fetch compares incomplete populations).
  Deals with empty/unknown `stageId` are EXCLUDED from all stage rows and
  reached math, counted per status in `unassigned`. Deals from other
  processes (defensive - the fetch is already scoped): treated as
  unknown-stage. `outcomes` = totals per status (including unassigned
  rows).
- `summarizeFeed`: keeps only entries with `inPeriod(entry.date, period)`;
  `outOfPeriodCount` = dropped rows. `byType` groups `type` verbatim
  ("" allowed), `byUser` groups `authorName` verbatim; rows sorted count
  desc, then name asc by PLAIN code-unit compare (`a < b`), never
  localeCompare. `total` = in-period rows.
- `summarizeTasks`: keeps tasks with non-empty `dateFrom` AND
  `inPeriod(task.dateFrom, period)`; `noDateCount` counts empty
  `dateFrom`, `outOfPeriodCount` counts dated-but-outside rows. Split by
  `isCompleted`; `byType` groups `typeName` verbatim, same sort.
- `summarizeForecast`: forecast side = open deals with non-empty `dateEnd`
  in period (`noDateEndCount` counts open deals with EMPTY `dateEnd`
  regardless of period - they can never be forecast). `weightedValueSum` =
  sum of `value * probability / 100` (2 decimals) over in-period rows
  where value is non-null AND probability is non-null AND within [0, 100]
  (evidence 12 guard); `weightedMissing` counts in-period rows failing any
  of those. Realization side = won/lost deals with `statusChangeDate` in
  period; `noStatusChangeDateCount` = closed deals (won+lost) with empty
  `statusChangeDate`. When `truncated` is true: `forecast.value.sum`,

## Execution notes (2026-08-06, all four tasks + fix pass done)

**Suite: 508 -> 644 tests, 9 feature/fix commits + this doc.** Orchestration
shape: 7 probe rounds BEFORE planning, a 3-lens critique panel over rev. 1

patched), 4 sequential implementers (one commit per task), an 18-agent
adversarial verification (4 lenses -> 14 findings -> 1 skeptic per finding:

modern-era MCP client.

**The headline defect the panel missed and verification caught:** a
calendar-invalid but regex-valid date ("2026-13-01") made `dayAfter` throw
a raw RangeError; the client saw `"Invalid Date"` with NO structuredContent
(outside the error contract), and - because `fetchTaskWindow` was not
async - the throw fired synchronously inside the `Promise.allSettled`
ARRAY LITERAL, orphaning the in-flight feed promise. With no
unhandledRejection handler, Bun 1.3.14 TERMINATES the process, so a bad
date plus any feed failure could kill a long-lived server. All four review
lenses found the date bug independently; a skeptic upgraded it by proving
the process kill end to end.

**Skeptics earned their tokens twice more.** (1) The reviewer-proposed
validator (`new Date(v).toISOString()` round-trip) itself THROWS on the
inputs it must reject - the shipped `isCalendarDate` NaN-guards through
`Date.parse` first, then round-trips to catch "2026-02-31" rolling to
March. (2) A proposed `basedOn.truncated` assertion for the deadline-wiring
regression was proven inert by mutation testing (true in both worlds); the
call-count assertion is what kills the mutant, verified by deleting
`deadlineAt` from both option builders and watching only the new tests
fail.

**Refuted-by-design decisions (do not "fix" these later):**
`ANALYZE_BUDGET_MS` is a PAGING gate, not a wall-clock bound - in-flight
pages run to completion, so a call may overrun by roughly one page (the
smoke saw 62 s once on a cold server); the CANCELLED entry guard after the
BAD_PARAMS return is correct (param validation touches nothing upstream);
`avgProbability` is NOT withheld on truncation (it is a property of the
fetched rows, not a period/ratio estimate); cross-status dedupe is not
needed (a deal that closes mid-sweep appearing on both sides is a
