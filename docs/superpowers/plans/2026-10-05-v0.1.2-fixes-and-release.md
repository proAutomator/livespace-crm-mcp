# v0.1.2: idle timeout, date and status filters, release (October 2026)

**Goal:** fix a transport bug that drops slow tool calls, close three small
filter gaps in `search_crm`, then release 0.1.2 so npm and the MCP Registry
carry the work merged since 0.1.1 (PRs #2-#5).

Each task is one commit on `release/v0.1.2`. The PR is merged with rebase,
not squash, so the commits stay separate on `main` (linear history).

## Evidence (2026-10-05)

- Bun 1.3.14 closes a connection that sends or receives nothing for
  `idleTimeout` seconds, default 10. Reproduced twice in a scratch script with
  a 13 s handler: a plain response and an SSE stream were both cut at 10 s,
  with the log line "request timed out after 10 seconds". `src/index.ts`
  calls `Bun.serve` without `idleTimeout`, while the execution deadline
  defaults to 90 s. `src/livespace/records.ts` records 14-19 s for one
  200-row deal page, so real `search_crm` and `analyze` calls can be cut.
  The unit and HTTP tests call `app.fetch` directly and never reach
  `Bun.serve`, which is why the suite stayed green.
- Read-only sandbox probe (counts and date bounds only):
  - `Deal/getAll` `modified: "not-a-date"` and `modified: "2026-02-31"`
    return the unfiltered list; `modified: "2099-01-01"` returns 0 rows.
  - `Deal/getAll` `status: "outdated"` returns 0 rows without an error,
    while `status: "bogus-status"` returns the unfiltered list. Upstream
    knows the label; the sandbox has no outdated deals.
  - `Contact/getAll` with `type: "contact"` and `type: "company"` honors the
    nested `created: {from, to}` condition exactly like deals:
    `{from: "2026-08-01"}` returned 39 persons and 32 companies, all created
    on or after that day; `{to: "2026-08-01 23:59:59"}` ended on that day;
    `{from: "2099-01-01"}` returned 0. `{from: "not-a-date"}` and the flat
    key `created_from` are ignored and return the unfiltered list.

## Task 1: Keep slow calls alive past Bun's idle timeout

Bun caps `idleTimeout` at 255 s. The runtime timeout has to outlast the
ingress and execution deadlines together, so the server, not Bun, ends a
slow call and the client gets the server's own timeout result.

- `src/config/server-env.ts`: lower `MAX_REQUEST_EXECUTION_TIMEOUT_MS` from
  300 000 to 180 000, so 60 s ingress + 180 s execution + 5 s margin fits
  under 255 s. Export:

  ```ts
  export const BUN_MAX_IDLE_TIMEOUT_SECONDS = 255;
  const IDLE_TIMEOUT_MARGIN_SECONDS = 5;

  export function idleTimeoutSeconds(config: ServerConfig): number {
    const deadlines = config.requestIngressTimeoutMs + config.requestExecutionTimeoutMs;
    return Math.ceil(deadlines / 1000) + IDLE_TIMEOUT_MARGIN_SECONDS;
  }
  ```

- `src/index.ts`: `Bun.serve({ ..., idleTimeout: idleTimeoutSeconds(serverConfig) })`.
- Tests first:
  - `tests/config/server-env.test.ts`: 300 001 and 180 001 are refused,
    180 000 is accepted; defaults give 105 s; the largest valid settings stay
    at or under 255 s.
  - New `tests/server/idle-timeout.test.ts`: start `src/index.ts` with
    synthetic settings, open a raw TCP connection, send a partial
    `GET /health` request, stay silent for 11 s, finish the request and
    expect `200`. Without the fix Bun closes the socket at 10 s.
  - `tests/security-contract.test.ts`: sixteen numbered requirements, the
    new test file in the map and in `test:security`.
- Docs: `docs/security.md` par. 2 (cap 180 s, new MUST on the runtime idle
  timeout) and par. 10 (requirement 16 with its regression proof), README
  and `.env.example` ranges.

## Task 2: Validate `modifiedFrom`

`modifiedFrom` takes the same `YYYY-MM-DD` shape check and calendar and
range checks as `createdFrom`, because upstream silently drops a date it
cannot read. The schema moves from a free `max(64)` string to `DATE_SHAPE`;
`dateHint` accepts the new field name; `createdRangeHint` becomes
`dateFilterHint` and checks `modifiedFrom` first. Tests first in
`tests/server/tools/search-crm.test.ts`.

## Task 3: Deal status `outdated`

Add `"outdated"` to the `status` enum of `search_crm` and to
`DealListOptions["status"]`. `analyze` keeps its open/won/lost windows: an
outdated deal is neither in the pipeline nor in won/lost realization, and no
sandbox data exists to test a new bucket. Whether `status: "all"` includes
outdated deals is unknown (no outdated deal on the sandbox), so the
description does not claim it. Tests first: the enum accepts the value and
forwards it to the fetcher.

## Task 4: Creation-date filter for persons and companies

`createdFrom`/`createdTo` leave `DEAL_ONLY_FILTERS` and apply to every kind.

- `src/livespace/records.ts`: move `createdFrom`/`createdTo` from
  `DealListOptions` to `ListOptions`; `createdCondition` takes
  `ListOptions`; `listContacts` sends the same nested `created` condition.
- `src/server/tools/search-crm.ts`: `listFor` forwards the dates for every
  kind; descriptions, the deal-only hint, instructions and README say the
  dates work for persons, companies and deals.
- Tests first: `tests/livespace/records.test.ts` pins the upstream
  `created` payload for persons and companies; `search-crm.test.ts` replaces
  the "created filter outside a deals-only search" rejection with forwarding
  for persons and companies.

## Execution notes

- Task 1 deviated from the plan in two places:
  - The first regression test (a raw socket that sent incomplete headers, or
    complete headers and no body, then stayed silent for 11 s) passed
    WITHOUT the fix. Bun does not time out a connection that is still
    sending its request; it times out one whose handler is running. The
    test now goes through a new `src/server/listen.ts` (the only
    `Bun.serve` call; `src/index.ts` uses it) with a handler that sleeps
    before answering.
  - An 11 s handler also passed without the fix. Bun checks idle sockets on
    a coarse tick, so the 10 s default fires between 10 and 14 s (12 s in
    both reproductions). The handler sleeps 15 s; without `idleTimeout` the
    test fails with "request timed out after 10 seconds". `bun test` now
    takes about 17 s instead of 2 s.
- Live evidence that real calls reach the window: through the HTTP server on
  the sandbox, `search_crm` for 100 deals at `detail: "full"` took 11.6 s on
  this branch. The same call on the old `main` took 9.7, 5.0 and 10.6 s and
  was not cut in those three tries, so the bug was not reproduced live; the
  15 s regression test is the proof.
- Sandbox smoke through the HTTP server on this branch, read-only, no data
  printed: `health` ok; `modifiedFrom: "2026-09-10"` returned 44 deals and
  `"2026-02-31"` returned BAD_PARAMS without an upstream call;
  `status: "outdated"` returned 0 deals without an error;
  `createdFrom: "2026-08-01"` returned 39 persons and 32 companies, all
  created on or after that day; a single-day person range returned only
  that day; `createdTo` on companies paginated normally.
- `modifiedFrom` boundary probe: `"2026-09-10"` returned the 44 deals
  modified that day from 00:27, `"2026-09-11"` returned none, so the
  filter is inclusive from local midnight and "on or after" is accurate.
- Not verified: whether `status: "all"` includes outdated deals, and the
  item-level label on a real outdated deal. The sandbox has none.
- Independent review (Fable 5.1, effort xhigh, read-only, Read/Glob/Grep
  only): ready to merge, no blocker. Confirmed in the SDK and Hono sources
  that the deadlines are sequential, that the execution deadline closes a
  deferred JSON response or SSE stream (SSE also sends keepalives every
  15 s), and that `listen(app.fetch, ...)` behaves like `fetch: app.fetch`.
  Applied in a follow-up commit: README states the old 300 000 ms maximum,
  the `outdated` description no longer says "expired" (it is a closing
  status with its own reason, not a deal past `dateEnd`), README says deal
  updates take open, won or lost only, `docs/security.md` notes the longer
  keep-alive window. Release notes must name both behavior changes: the
  180 s cap and `modifiedFrom` accepting only `YYYY-MM-DD`.
- Kept on purpose: the reviewer named `server.timeout(request, 0)` per
  request as an alternative that would keep the 300 s cap and the 10 s
  keep-alive window. Not verified at runtime and it would need a reworded
  MUST, so the tested `idleTimeout` stays; revisit if someone needs more
  than 180 s.
- Out of scope, noted for later: `mapDealCount` drops the `outdated`
  counter that `deal_count` carries; `update_records` cannot set
  `outdated` (upstream support unknown).
- Local gate before the release commit: `bun install --frozen-lockfile`,
  `bun audit` (no vulnerabilities), typecheck, 1212 tests, the security
  suite and `git diff --check` all pass.
